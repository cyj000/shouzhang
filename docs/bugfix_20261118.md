## 2. 根因分析（对照设计口径）

静态审计保存链路 `EntryController.save → EntryRepository.save → EntryDao/oplog/tag/telemetry`，逐项核对：

**SQL 口径核对（已排除）**：
- `entries` insert：23 列 / 23 占位符 / 23 参数，一致 ✓
- `oplog`、`entry_tags`、`tags`、`telemetry_events` insert 列/值均匹配 ✓
- 金额全链路 int 分（`amountCents`），无 double ✓
- passphrase 为 base64url，不含单引号，`PRAGMA key` 无注入/语法问题 ✓

**确认的缺陷（已修复）**：
1. **`save()` 全程无 try/catch**（直接对应"保存不成功"现象）：
   - 原实现中 `await repos.entries.save(entry)` 及后续标签/埋点/prefs 任一步抛异常，异常直接冒泡到 UI 的 `onPressed` async 回调，成为未捕获异常——不弹 SnackBar、不清空表单、不设置 `state.error`。用户看到的就是"点了没反应"。
   - 修复：整体 `try/catch`，异常转 `state.error`（可读提示），保留表单，解锁按钮。
2. **无 `isSaving` 防连点锁**（3.3 根因1）：
   - 原按钮点击立即生成新 `entryId`，连点产生两条不同 UUID 账目、竞态写库。
   - 修复：`EntryFormState.isSaving` 状态锁，保存中按钮禁用并显示进度圈。
3. **写操作非原子**（3.3 根因3）：
   - 原实现账目/标签/埋点分散多次 `await`，中途失败留下"账目写了但标签/埋点没写"的半截数据。
   - 修复：全部写操作包进 `repos.db.transaction()`，成功提交才反馈、失败整体回滚。
